Estrategia de testing — rollback transaccional

Por qué crear/borrar datos de prueba contra el Neon real no deja rastro. Ver docs/TESTING.md.

Caso normal — la gran mayoría de los tests
① Arranca el método de test
@Transactional a nivel de clase abre una transacción (TX-A) para todo el método.
↓
② MockMvc.perform(...) → Controller → Service
El service tiene su propio @Transactional, pero con propagación REQUIRED por defecto simplemente se une a TX-A — no abre una transacción nueva.
↓
③ Repository.save() → persist()
Con GenerationType.UUID el id se asigna en memoria, pero el INSERT real queda encolado en el persistence context — no viaja a Postgres todavía.
↓
④ Assertions sobre la respuesta HTTP
MockMvc devuelve la respuesta sin haber hecho un commit real.
↓
ROLLBACK
⑤ Termina el método → Spring revierte TX-A
Todo lo encolado se descarta. La base real queda exactamente igual que antes del test.
Excepción — efectos reales de DB (2 tests)
@Transactional(propagation = NOT_SUPPORTED)
Sin TX de test, cada POST/DELETE abre su propia transacción real, con flush/commit de verdad.
↓
COMMIT REAL
createWithDuplicateNameReturnsConflict
Postgres detecta el índice único violado → DataIntegrityViolationException → GlobalExceptionHandler → 409.
↓
COMMIT REAL
nameAndSlugCanBeReusedAfterSoftDelete
Crea → borra (soft-delete real) → crea de nuevo con el mismo name/slug → 201, prueba que el índice parcial libera el valor.
↓
CLEANUP MANUAL
finally { tagRepository.deleteById(id) }
Sin rollback automático acá — hay que borrar a mano la(s) fila(s) que quedaron activas.
Media — sin tocar R2 real
@MockitoBean S3Client
Reemplaza el bean real antes de que se construya el contexto — el @Bean de R2Config ni se ejecuta.
↓
verify(s3Client).putObject(...)
Se verifica que se llamó con los parámetros esperados, sin red ni credenciales reales.
