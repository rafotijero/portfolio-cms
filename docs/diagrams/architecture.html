Arquitectura en capas — portfolio-cms

Controller → Service → Repository → Domain, con dos superficies de entrada distintas (público / admin). Ver docs/ARCHITECTURE.md.

PÚBLICO
GET /api/v1/**
Sin token. Solo lectura, solo contenido PUBLISHED donde aplica.
ADMIN
/api/v1/admin/**
Requiere Authorization: Bearer <jwt> con rol ADMIN.
↓ ↓
SecurityFilterChain (config/SecurityConfig.java)
JwtAuthenticationFilter valida el JWT si viene el header (nunca consulta la base). Lista blanca: GET /api/v1/** público, /api/v1/admin/** exige hasRole("ADMIN"), /api/v1/auth/** denyAll salvo POST login, todo lo demás denyAll por defecto.
↓
api — Controller (PostController, AdminPostController, ...)
Capa delgada: recibe el request, valida con Bean Validation (@Valid), delega al service. Nunca expone entidades directo.
↓
service — lógica de negocio + límite transaccional
@Transactional(readOnly = true) a nivel de clase, @Transactional explícito en los métodos de escritura. Acá vive el mapeo a DTO — tiene que pasar dentro de la transacción porque open-in-view está deshabilitado.
↓
repository — Spring Data JpaRepository
Interfaces sin implementación propia; Spring Data genera las consultas.
↓
domain — entidad JPA
Mapea 1:1 con las tablas que gobierna Flyway (ddl-auto: validate).
DATOS
PostgreSQL (Neon)
Única fuente de verdad del esquema.
↓
api.dto — record (PostDetailDto, ProjectDto, ...)
Forma que ve el cliente por HTTP. Errores no manejados por el controller suben a GlobalExceptionHandler (ej. UNIQUE duplicado → 409).
